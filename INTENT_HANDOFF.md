# Monk → Intent: orchestration handoff

**Purpose:** Monk produces product specs that are grounded in research and, by design, stops at
"here is a fully-formed spec, ready to build." This document is for the Intent team: how Intent
picks up from that point and orchestrates the implementation.

---

## 1. Division of responsibility

| | Owns | Produces |
|---|---|---|
| **Monk** | Authoring: research capture (signals) → synthesis (insights) → framing (specs) → grouping (initiatives). | A workspace of plain markdown files, and — per spec — a **build brief** (§3). |
| **Intent** | Execution: taking a spec + its context to working, merged code. Spawning/coordinating coding agents, tracking progress against acceptance criteria, surfacing blockers. | Working software; optionally, status written back to the workspace (§6). |

The seam between them is the build brief. Everything Intent needs to *start* is in it. The full
workspace is available if Intent needs to go deeper (§5).

Monk deliberately does **not** call an LLM or run agents itself. Assembling the hand-off and
staying out of the execution loop is the design stance — that loop is Intent's.

---

## 2. Where the content lives

Monk stores everything as plain markdown in a folder the user points it at — intended to sit
**inside the product repo** so it's versioned alongside the code it describes. Layout, per-file
formats, id conventions, and the relationships between records are all documented in
**`MONK.md`** at the root of that folder. `MONK.md` is auto-generated by Monk and kept current;
treat it as the canonical schema reference.

Key facts an integrator should know up front (full detail in `MONK.md`):

- Frontmatter is a **single line of JSON** between `---` fences, not YAML.
- Global records (specs, signals, insights, activities, initiatives, sections, documents) use
  UUIDs; board cards and connections use small integers.
- A spec is a folder (`<spec-uuid>/`) containing `spec.md`, `design.md`, `plan.md`, and a
  `board/` subfolder.
- Board `signals/` and `insights/` files are **pointers** to the global records, not copies —
  editing the global record changes it everywhere it's linked.
- `standards/` and `product-knowledge/` are two fixed sections with literal ids; their
  documents are what the build brief pulls its Standards and Product knowledge sections from.

---

## 3. The build brief

Monk's **"Start build"** action (on a spec's page) assembles one markdown document. Today it
opens that document as text for the user to hand off manually; writing it to a path is a small
change on Monk's side if Intent prefers file-drop (§4).

### Structure and semantics

Sections appear in this order. The framing of each matters as much as the content:

| Section | Assembled from | How Intent should treat it |
|---|---|---|
| **Preamble** | fixed | States that this is an execution hand-off, that Standards are constraints, and that unresolved Open Questions are stop conditions. |
| **Standards** | every doc in `standards/` | **Hard constraints.** Design system, accessibility, coding conventions. Output must satisfy these whether or not the spec restates them. Treat like a linter that can't be disabled. |
| **Product knowledge** | every doc in `product-knowledge/` | **Judgment context.** Vision, prior decisions, user facts. Use to resolve ambiguity the spec doesn't cover; never to override an explicit spec decision. |
| **Initiative** | the spec's initiative, if it has one | Shared context for a group of related specs — broader than this spec, narrower than product-wide. Omitted entirely if the spec has no initiative. |
| **Problem / Goals** | spec Overview | Why the work exists; what success is. |
| **Non-goals** | spec Overview | **Binding scope fence.** An autonomous orchestrator drifts here unless it treats Non-goals as a hard boundary. Do not expand past it. |
| **Open questions** | spec Overview checklist | **Stop conditions.** Any unresolved item → ask a human, or make a *documented, flagged* assumption. Never silently decide. Resolved (checked) items are not included. |
| **Design** | spec Design tab | The intended approach. Follow it; fill gaps it leaves consistent with Standards + Product knowledge. |
| **Plan** | spec Plan tab | Task breakdown / sequencing, where the author provided one. May be sparse. |
| **Acceptance criteria** | spec Overview checklist | **The exit condition.** Orchestrate until every item can be checked. Items are `{text, checked}`; a subjective criterion is a human sign-off gate. |

### Example

A real brief (content is illustrative):

```markdown
# Build brief: Signal source simplification

This is a hand-off for an agent to execute, assembled from Monk. Standards below are
constraints, not suggestions — satisfy them whether or not the spec repeats them. If
anything under Open Questions is still unresolved, stop and ask (or make a documented,
flagged assumption) rather than deciding silently.

## Standards
_Contracts to build to — design system, accessibility, and any other house rules below. Non-negotiable._

#### Design system

Use the shared Button/Field/Card primitives. Never hardcode a color — reference the token scale in lib/theme.js.

#### Accessibility

WCAG 2.1 AA. Every interactive element keyboard-reachable; visible focus ring; 4.5:1 text contrast.

## Product knowledge
_Background and prior decisions. Resolves gaps the spec below doesn't cover — never overrides something the spec explicitly decided._

#### Vision

Keep research traceable to the work it justifies. No lock-in — everything is plain files.

## Initiative
_This spec is one of several under an initiative. The following is shared context for all of them — broader than this spec, narrower than the product-wide knowledge above._

### Card UX pass
Reduce visual clutter across signal / insight / spec cards. Each change should remove a control, not add one.

## Spec: Signal source simplification

### Problem
The signal card shows a From-activity / Other mode selector plus a free-text source field. For the common case (no activity) that is two controls doing nothing.

### Goals
A signal is either tied to an activity or it is not. One optional Activity field, nothing else.

### Non-goals
_Scope fence — treat as binding, not optional._

Not changing how insights reference signals. Not touching the Discovery board layout.

### Open questions
**Unresolved — stop and ask, or make a documented, flagged assumption. Do not decide silently:**

- [ ] Should a detached signal keep the old activity name anywhere?

### Design
Drop the selector. Activity becomes an optional field using the existing AddField reveal pattern (like Link/Author). A small x clears it back to none.

### Plan
1. signalModel + markdown. 2. SignalCardBody. 3. App.deleteActivity detach path. 4. Update the three test suites.

### Acceptance criteria
_The exit condition — build until every box below can be checked._

- [ ] No mode selector renders on a signal card
- [ ] source is null or {type:"activity",activityId}; the text variant is gone from the model and markdown round-trip
- [ ] Deleting an activity sets its signals source to null (verified by test-undo.mjs)
```

## 4. Delivery mechanism — options

Monk is flexible here; pick whichever fits Intent:

1. **File drop** — "Start build" writes the brief to a known path (e.g.
   `<workspace>/.monk/briefs/<spec-uuid>.md`, or `<spec-uuid>/build-brief.md`). Intent picks it
   up. No coordination protocol needed. *Small change on Monk's side.*
2. **Explicit invoke** — the user triggers Intent with the brief content (paste, CLI arg, or an
   API call Intent exposes). *Supported today* — "Start build" already produces the text.
3. **Directory watch** — Intent watches the workspace folder; a new/changed brief file kicks off
   a run.

**Recommendation:** start with (1) or (2); add (3) later if the workflow warrants it.

---

## 5. Going beyond the brief

The brief is a curated slice of the workspace. If Intent needs the full research graph — to
show an operator the provenance behind a goal, or let them drill from an acceptance criterion
back to the signals that motivated it — the complete content is the markdown in the workspace
folder, and `MONK.md` documents every format and relationship. Traversal an integrator would
likely want:

- `spec.initiativeId` → `initiatives/<id>.md`
- a board's `insights/<id>.md` pointer → `insights/<id>.md` → its `sources[]` → `signals/<id>.md`
- `signal.source.activityId` → `activities/<id>.md`

---

## 6. Writing back (proposed — Phase 2)

For a first version, Intent **consumes and does not write**. If closing the loop is wanted:

- Intent may check off **acceptance criteria** as tasks land — edit the `acceptanceCriteria`
  array in `<spec-uuid>/spec.md` (`{text, checked}` items), following `MONK.md`'s format, and
  bump `updatedAt`.
- Intent may set spec `status` to `shipped` on completion.
- Everything richer — writing Design/Plan, creating specs or insights — stays out of scope.
  That's authoring, which is Monk's job.
- **Caveat:** Monk currently loads the workspace once when it connects and does not watch for
  external edits, so write-backs appear in Monk on its next reload. A focus-triggered re-scan
  (Monk re-reads the folder when its tab regains focus) is planned and would make this feel live
  for the tab-away-to-Intent, tab-back-to-Monk loop.

---

## 7. What the Intent team needs to decide

- **Delivery** — file-drop, explicit invoke, or directory watch (§4)? And the path/convention if
  file-drop.
- **Write-back scope** — is §6 (acceptance criteria + status) in scope for v1, or strictly
  consume-only?
- **Escalation** — how do unresolved Open Questions and subjective Acceptance Criteria get in
  front of a human, and who is that human?
- **Access** — does Intent need read access to the whole workspace (§5), or just the brief?

---

## 8. Phasing

| Phase | Monk side | Intent side |
|---|---|---|
| **1** | "Start build" writes the brief to an agreed path (or nothing — user pastes). | Consume a brief, orchestrate against it, report status out-of-band. No write-back, no workspace traversal. |
| **2** | Focus-triggered re-scan so write-backs surface without a manual reload. | Write acceptance-criteria checkmarks and spec `status` back to `spec.md`. |
| **3** | — | Watch the workspace for new/changed briefs; full two-way sync. |
